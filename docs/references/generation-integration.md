# Generation integration findings

Research date: 2026-11-21. Documentation and upstream source inspection only. No dependencies installed, worker started, provider credentials inspected, or paid requests made. These findings inform the separate implementation plan; they do not change accepted product requirements.

## Concrete local shape

Use one TypeScript project with `frontend/src/app`, `frontend/src/generation`, `frontend/src/server`, and `frontend/src/story`. Next and the generation worker run as separate processes from the same project. The worker entry is `frontend/src/generation/mastra/index.ts`; generation owns integration initialization, versioned workflows, agents, and provider adapters. Server persistence lives under `frontend/src/server`, and shared story contracts under `frontend/src/story`. Keep worker runtime and provider clients out of browser imports. No workspace packages or monorepo are needed.

For the first integration use the documented Mastra HTTP server, rather than adding another server framework or beta Connect transport. Register `serve({ mastra, inngest })` from `@mastra/inngest` at **`/inngest/api`**, with `method: 'ALL'`, in the worker's Mastra `server.apiRoutes`. Worker port: 4111; Next port: 3000; Inngest UI/event API: 8288. Bind local processes to localhost. `/api/inngest` conflicts with Mastra's default reserved `/api` prefix and throws at startup. Do not add a duplicate Next execution route. The documented Next adapter is an alternative when Next itself owns execution, which is outside this chosen process split. [Mastra integration](https://mastra.ai/integrations/deploy/inngest).

Future setup scripts should run pinned local binaries from the `frontend/` package directory: `pnpm exec mastra dev --dir src/generation/mastra` and `pnpm exec inngest-cli dev -u http://localhost:4111/inngest/api`. Upstream [CLI source](https://github.com/mastra-ai/mastra/blob/main/packages/cli/src/index.ts) defines `mastra dev --dir <dir>` as the Mastra folder option. Verify its entry discovery and environment-file resolution with the chosen release during the fixture smoke test. These are proposed commands, not scripts available today. Both the web event producer and worker need explicit local Inngest mode (`INNGEST_DEV=1`); use a shared stable Inngest app ID. The integration also documents explicit `baseUrl: 'http://localhost:8288'` and `isDev: true`. The dev server needs no cloud account, event key, or signing key. Keep the three processes under future `pnpm --dir frontend dev` supervision with explicit shutdown behavior. [Inngest local development](https://www.inngest.com/docs/local-development).

## Package and compatibility gate

Candidate worker runtime packages: `@mastra/core`, `@mastra/inngest`, `@mastra/pg`, `inngest`, and `zod`; add `@mastra/observability` for tracing configuration. Development packages include `mastra` (CLI), `inngest-cli`, TypeScript, and Node types. Do not add the obsolete `@inngest/realtime` package or its middleware: Inngest v4 includes realtime. Use Mastra's direct `openai/gpt-6.2-sol` model configuration for text; install provider SDK packages only where the actual embedding/media adapter needs them. Google narration uses `@google/genai`; image generation can use the `openai` SDK or a typed REST adapter.

The integration docs require `inngest@^4` and Inngest Dev Server **>=1.18.0**. Mastra core, CLI, and integration upstream manifests require Node **>=22.13.0**. The frontend package already pins Node in `.node-version`; verify that pin against the chosen worker release rather than inheriting a global version or restarting frontend scaffolding.

**Exact installable pins remain unresolved.** Direct npm registry reads failed in the restricted shell and browser fetcher. Upstream `main` manifests returned prereleases (`@mastra/core` 1.86.0-alpha.3, `mastra` 1.40.2-alpha.3, `@mastra/pg` 1.37.1-alpha.0, and a cached `@mastra/inngest` 1.10.8-alpha.0), while the current integration changelog already lists 1.11.4. These are evidence of release/cache mismatch, not a coherent recommended installation set. Do not copy these prereleases into the plan as proven stable pins.

Observed manifest compatibility ranges, to recheck against the actual chosen release metadata: integration core peer `>=1.79.1-0 <2.0.0-0`, Zod peer `^3.25.0 || ^4.0.0`, Inngest dependency `^4.5.0`; PG core peer `>=1.84.0-0 <2.0.0-0`; CLI core peer `>=1.85.1-0 <2.0.0-0`. The integration changelog mentions **core 1.85.0 + integration 1.11.4**, but core 1.85.0 does **not** satisfy the observed CLI peer floor 1.85.1. Combining that changelog pair with this CLI would be incoherent; no complete package set is recommended here. Resolve a released core/CLI/integration/PG set whose actual peer ranges intersect. Inspect exact version, engines, peer dependencies, and exports for every selected package, lock exact versions, then run a fixture-only worker smoke test before calling the integration verified. Sources: upstream [integration manifest](https://raw.githubusercontent.com/mastra-ai/mastra/main/workflows/inngest/package.json), [core manifest](https://raw.githubusercontent.com/mastra-ai/mastra/main/packages/core/package.json), [CLI manifest](https://raw.githubusercontent.com/mastra-ai/mastra/main/packages/cli/package.json), [PG manifest](https://raw.githubusercontent.com/mastra-ai/mastra/main/stores/pg/package.json), and [integration changelog](https://raw.githubusercontent.com/mastra-ai/mastra/main/workflows/inngest/CHANGELOG.md).

## Storage, progress, and recovery

`PostgresStore` from `@mastra/pg` accepts a connection string or shared `pg.Pool`, supports `schemaName`, and initializes its own storage tables. It can use the **same local PostgreSQL database** as the application; a separate `mastra` schema is a useful ownership boundary, not a requirement for a second database/service. Keep app migrations and business records separate from adapter-managed tables. A supplied pool remains caller-owned. Decide explicitly whether adapter initialization runs at development startup or is separately managed with `disableInit`; avoid two migration owners for the same tables. [PostgreSQL adapter](https://mastra.ai/integrations/databases/postgresql).

Mastra defines the workflow; its Inngest integration supplies the execution engine. Inngest retains completed step results and schedules retry/resume. Mastra storage holds runtime snapshots and observability. Application PostgreSQL owns job state, reservations/spend, chapter publication, evidence, and asset references. Do not create an additional application scheduler that runs failed stages independently of Inngest. A database outbox for reliable event dispatch is a handoff/reconciliation mechanism, not a second workflow coordinator. The application progress API should read authorized canonical database records, so refresh, observer disconnect, and worker restart do not erase progress. Diagnostic realtime updates may supplement that API.

Explicitly set a finite workflow `retries` value: the integration documents **0 by default**, so merely choosing Inngest does not establish crash recovery. Nested workflows need their own setting. Step-code failures use per-step retries/retry configuration; bound those independently of function transport retries. Checkpoint return values should contain record IDs/compact results rather than media blobs. These retry semantics require a fixture crash/resume proof before relying on them.

Retain operation/asset idempotency records across the provider-call/commit uncertainty window. Replay cannot guarantee external effects execute once. Tests must interrupt execution after a saved result, during a step, and after a fake provider effect but before result commit; verify that finished chapters stay stable, reservations reconcile, and effects are reused or explicitly marked uncertain.

Inngest resumes with current code and saved results matched by step ID; version labels alone do not retain old logic. Preserve stable step IDs for compatible changes. For incompatible contracts use a new workflow/function ID with exclusive version routing, retain the old implementation while jobs remain active, and verify both a paused old run and a fresh new run. [Inngest versioning](https://www.inngest.com/docs/durable-execution/guides-and-advanced/versioning).

## Selected providers: existence versus access

| Selected model | Official documentation result | Live integration gate |
| --- | --- | --- |
| `gpt-6.2-sol` | Exact model exists; official page documents text output, function calling, structured output, and Responses API support. | Project access, allowed model configuration, account limits, adapter behavior, and a budgeted structured-output smoke test remain unverified. |
| `gpt-image-2.6-sunburst` | Exact model exists; official page documents image input/output and generation/edit interfaces. | Account access and precise SDK request/response support remain unverified. Persist generation parameters and returned assets/provenance. |
| `gemini-3.8-flash-tts` | Exact model exists in Google's TTS guide; text input/audio output. Guide requires `@google/genai >=2.24.0` or REST and shows the Interactions API. | Check actual chosen SDK types, model access, voice, encoding, and timestamp/subtitle alignment; do not assume older `generateContent` examples apply unchanged. |
| `text-embedding-3-small` | Exact embedding model exists in the official OpenAI catalog. | Verify configured dimensions against pgvector schema and index/query code before live ingestion. |

Official sources: [Sol](https://developers.openai.com/api/docs/models/gpt-6.2-sol), [Sunburst](https://developers.openai.com/api/docs/models/gpt-image-2.6-sunburst), [Gemini TTS](https://aistudio.google.com/docs/speech-generation), [embedding](https://developers.openai.com/api/docs/models/text-embedding-3-small). No selected model needs a silent replacement based on this research. Documentation existence does not prove the user's account has access. An unavailable model must fail its live preflight explicitly and remain configurable by stage; changing the selected default requires a deliberate decision.

Prepared-data mode must construct no paid provider client and require no OpenAI, Gemini, Tavily, or OpenRouter key. It should exercise the same worker stages, validation, persistence, chapter progress, and recovery with saved inputs and outputs. Optional provider credentials belong only in live-mode validation. Actual integration testing, exact stable package pin resolution, and authenticated model preflight are unfinished implementation work.
